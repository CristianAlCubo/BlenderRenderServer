## Context

Greenfield monorepo. No existing code or consumers. Target deployment is a Debian 13 server running Docker; orchestration via `docker compose` only. The system must let a user upload a Blender project (`.blend` or `.zip`), render it headless on CPU or NVIDIA GPU, encode video with FFmpeg, and preview/download the result through a polished web UI. The first milestone is a working end-to-end pipeline; architecture polish and UI refinement follow.

Hard constraints (non-negotiable): Fastify + TypeScript backend, React + Vite + TypeScript + shadcn/ui frontend, REST over Fastify, relative `/api/*` consumption, Vite dev proxy, Nginx as the sole public HTTP entry (production), WebSocket at `/api/ws`, SQLite persistence, Redis + BullMQ queue, Blender headless CLI, FFmpeg encoding, Docker from the first commit.

## Goals / Non-Goals

**Goals:**

- End-to-end pipeline: upload → validate → enqueue → render (Blender) → encode (FFmpeg) → output → preview/download.
- Clean separation of HTTP (thin Fastify handlers), business logic (services), persistence (repositories/Drizzle), queue (BullMQ), render (engine abstraction), storage (filesystem), and realtime (WebSocket).
- Single-origin production deployment behind Nginx; relative API URLs end-to-end.
- Real-time progress and logs, worker heartbeats, and lightweight system monitoring.
- A foundational architecture that supports adding multiple workers and additional render engines later, and adding auth later.
- Functional correctness enforced by URL validation, safe subprocess argument arrays, and filesystem access controlled through the API.

**Non-Goals:**

- Authentication/authorization (private/self-hosted initially, but structured so auth can be added later).
- A Kubernetes deployment or a full distributed scheduler.
- A comprehensive monitoring system; only lightweight CPU/RAM/disk/GPU reporting.
- Users/teams/permissions (single implicit user).
- Replacing Flamenco-style orchestration semantics; this is a direct Blender CLI render server.

## Decisions

### 1. Monorepo layout (npm workspaces)
```
backend/          Fastify API + Drizzle + BullMQ producer
worker/           BullMQ consumer + BlenderRenderEngine + FFmpeg (shared TS code with backend)
frontend/         React + Vite + shadcn/ui + TanStack Query
packages/shared/  shared types/enums/schemas (JobStatus, ComputeMode, OutputType, API DTOs)
docker/           nginx/default.conf, Dockerfiles, compose files
```
- **Why**: single repo with shared types via TS project references avoids enum/type drift between API, worker, and UI.
- **Alternative considered**: separate repos/packages published to npm — overkill for a self-hosted tool; adds release friction.

### 2. Backend: Fastify with modular vertical slices + fastify-autoload-style registration
Routes carry JSON Schema (params/querystring/body/response). Handlers delegate to service modules; services call repository modules (Drizzle) and the queue. Shared `app.ts` (decorators, plugins, routes) vs `server.ts` (bind + lifecycle) so tests can inject against a configured instance without binding.
- **Why**: satisfies the Fastify requirement, gives real runtime validation, keeps handlers thin.
- **Alternative considered**: Express/NestJS — excluded by hard constraint; Fastify gives native schema validation and first-party plugin ecosystem.

### 3. Persistence: SQLite via Drizzle ORM
SQLite is the source of truth. Redis is ephemeral queue state only. `jobs`, `job_outputs`, `job_logs`, `workers` tables. Logs stored as a `render.log` file on disk with a small `job_logs` table for structured/streamed entries; full text file is not stored in SQLite.
- **Why**: zero extra service, single-file durability, trivially persisted via bind mount; Drizzle gives type-safe queries and migrations.
- **Alternative considered**: Postgres — heavier, unnecessary for single-node self-host; excluded by constraints.

### 4. Queue: Redis + BullMQ (`render` queue)
Fastify enqueues after DB insert; worker consumes. Retry policy bounded (default 3 attempts). State transitions (progress, started, completed, failed, cancelled) are persisted to SQLite by the worker/service, so historical state never depends on Redis. Job IDs are generated by the app (not Redis), so the API owns identity.
- **Why**: BullMQ is the standard, well-supported Redis queue; matches the constraint.
- **Alternative considered**: in-process queue (loses multi-worker future), RabbitMQ/Kafka (excluded, heavy).

### 5. Render engine abstraction
`interface RenderEngine { render(job): Promise<RenderResult>; cancel(jobId): Promise<void>; getCapabilities(): Promise<RenderCapabilities> }` with `BlenderRenderEngine` as the first implementation. FFmpeg is invoked by the worker as a separate process after frames are produced (not inside the engine's `render`).
- **Why**: enables later engines without rewriting the worker; keeps FFmpeg as an orthogonal encode step.
- **Alternative considered**: hard-coding Blender in the worker — violates extensibility goal.

### 6. Worker process isolation + process management
Separate `worker/` entrypoint that starts BullMQ `Worker` consumers. Blender/FFmpeg run via `spawn(command, argsArray)` (never a shell string), stdout/stderr piped, errors detected via exit code + stderr heuristics. `MAX_CONCURRENT_RENDERS` caps BullMQ concurrency. A crash of Blender fails the job (or retries) without killing Fastify/Redis/Worker.
- **Why**: satisfies constraint; array args prevent shell injection; per-job subprocess isolation contains crashes.

### 7. Storage: local filesystem under `/data`
```
/data/database/app.db
/data/projects/<job-id>/{project.blend, assets/, logs/render.log}
/data/renders/<job-id>/{frames/, output.mp4|png}
```
Mounted as a persistent volume. Safe ZIP extraction with path-traversal/symlink/absolute-path protection; filenames sanitized. Outputs served only through `GET /api/jobs/:id/output` (and a preview route), never by exposing `/data`.
- **Why**: meets constraint; keeps user-uploaded materials isolated per job.

### 8. Realtime: `@fastify/websocket` at `/api/ws`
A single WS route broadcasts typed events (`job.*`, `worker.*`). Events are published from services/worker via an in-process event hub, with the worker posting back to the hub over a shared bus. The bus is Redis-based (BullMQ events + a pub/sub channel) so worker events reach every Fastify instance even with future scaling. Clients reconnect automatically; TanStack Query re-syncs REST state on reconnect.
- **Why**: satisfies `@fastify/websocket` constraint; Redis pub/sub keeps realtime correct across processes.

### 9. Frontend architecture
Vite + React Router + TanStack Query. API client uses relative `/api/*` only. Vite dev server proxies `/api` and `/api/ws` to Fastify. Production is a static build served by Nginx (or a dedicated `frontend` container). shadcn/ui components, Tailwind, dark mode, skeleton/empty/error states, toasts, badges, progress bars, drag-and-drop upload.
- **Why**: matches constraints; relative URLs mean no environment-aware API base.
- **Alternative considered**: absolute API base via `import.meta.env` — explicitly rejected by constraints.

### 10. Deployment topology
`docker compose up -d` runs: `nginx` (ports 80:80, sole public entry), `frontend`, `backend`, `worker`, `redis`. Nginx `location /api/` → `proxy_pass http://backend:3000` (path preserved) with WS upgrade headers; `location /` serves frontend static assets with `try_files … /index.html`. Backend/redis/worker expose no host ports. `docker-compose.gpu.yml` adds NVIDIA runtime + device passthrough for the worker. Worker detects compute capabilities (CPU/CUDA/OptiX) and reports them.
- **Why**: matches constraints; simplest clean topology where Nginx serves built assets directly.
- **Alternative considered**: dedicated frontend container serving its own assets behind Nginx — kept as an option; chosen: build assets into the Nginx image for fewer moving parts.

### 11. Dev workflow
Local dev runs `docker compose up -d redis`, then backend (`tsx watch`), worker, and Vite dev server natively. Vite proxies `/api` and `/api/ws`. No env-aware base URL in React.

## Risks / Trade-offs

- **[Blender crashes on malformed projects]** → Worker treats non-zero exit / stderr markers as job failure; bounded BullMQ retries (3); error message persisted; Fastify/Redis unaffected.
- **[Large uploads (up to 10GB) exhaust memory]** → Streaming multipart writes directly to disk (`@fastify/multipart` file write path); `MAX_UPLOAD_SIZE` enforced; Nginx `client_max_body_size` aligned.
- **[ZIP bombs / path traversal]** → Size caps, entry-count/file-size limits, sanitize + strip `../`/absolute paths, reject symlinks, extract into a per-job sandbox dir, verify `.blend` presence.
- **[Zombie render processes on cancel]** → `cancel()` kills the spawned Blender/FFmpeg child group; OS-level cleanup on worker shutdown.
- **[Profiles/jobs rely on correct FPS/resolution]** → Parse Blender scene/FPS via CLI introspection where possible; default to Blender's render settings rather than hardcoded 30 FPS.
- **[Single worker concurrency risk]** → `MAX_CONCURRENT_RENDERS=1` default; BullMQ concurrency guard; multi-worker simply scales by adding replicas consuming the same queue.
- **[Redis is not durable for job state]** → SQLite remains source of truth; UI REST reads always hit SQLite; Redis only drives queue order.
- **[GPU availability varies]** → Worker probes capabilities; reports CPU/CUDA/OptiX; GPU deployment is an opt-in compose overlay; app degrades gracefully to CPU.

## Migration Plan

- **Initial release**: greenfield; no migration. `docker compose up -d` provisions volumes (`/data`) and SQLite schema via Drizzle migrations on backend start.
- **Rollback**: revert commit and re-run compose; data stays in `/data` (schema migrations are additive-only in early releases).
- **Data**: `/data` bind mount is the single persistence point; documented for backup/restore.
